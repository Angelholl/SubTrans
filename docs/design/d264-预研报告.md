## 批1 FTS5 三同步策略 spike（真实 tm.db 拷贝，7,465 行/3.0MB）

| 维度 | A external-content+列限定触发器 | B 显式双写（store/store_batch） | C 重建全量刷+指纹判亚 |
|---|---|---|---|
| 建索引 | rebuild 0.45s | 增量 0.031ms/行（每批 30 新句 ≈0.9ms） | **全量 0.17s** |
| BM25 查询 | 原文 0.03ms | 原文 0.01ms/**归一 0.02ms**（真双口径） | 同 B 面 |
| 热路径对拍（每批 30 lookup+命中 UPDATE，6000 次） | 54.0ms/批（基线 52.6，差≈噪声） | **构造上零热路径成本**（实测 57.0 亦噪声带） | 零 |
| 对真实批占比（C1 红线 ±5%） | ≤0.02% ✅ | 0% ✅ | 0% ✅ |
| NFKC 归一列 | ❌ 纯 SQL 触发器无法计算 | ✅ python 端计算 | ✅ |
| 库体积 | 索引量级=内容量级（WAL 合并后计，主文件读数 +0B 为未 checkpoint 假象） | 同 A 量级 | 同 |

- **C1 判定：三策略全过红线**（列限定触发器实证豁免 hit_count UPDATE——`UPDATE OF`
  内容列清单生效，热路径差在噪声带内）。
- **推荐：B（显式双写）**——唯一原生支持真双口径（NFKC 归一列）且热路径构造零成本；
  审计点仅 store/store_batch 两处。A 为备选（有 NFKC 列硬伤）；C 为 B 审计失败时的
  兜底（全量刷 0.17s/7.4k 行，即便每次打开重建也仅亚秒级）。
- **C2 义务坐实**：演示证明"先建 FTS 后做 DROP+RENAME 表重建迁移"即损面——批1 实现
  必须：FTS 创建排 `_init_db` 迁移链（ensure_source_name_column→ensure_direction_columns）
  末端 + 任何表重建迁移连带重建 FTS 面 + "旧库→自动迁移→FTS 可用"幂等用例。

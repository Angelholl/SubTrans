# 阶段 0a · Token 归一提案（type scale / spacing / radius / 表面三层）

> 3.1 UI 重塑计划 · 阶段 0a 交付物之五。对应审计报告 P0-1 / P0-2 / P0-3 / P1-10。
> **本提案是钉④ 的冻结对象候选**：冻结的应是"归一后的定稿值"，不是今天的散落现状。
> 方向已锁：现代极简 SaaS / Notion-Vercel 系 / `#3B82F6`，**本提案不提出任何新风格，也不提出新色板**（表面三层只做"层分配"调整，色值全部复用 handoff §5 既有值）。

## 0. 结论先行

1. **钉④ 的机器范围比政策口径窄得多**：`tests/test_ui_phase3_redlines.py:112-121` 实际只冻结 4 条 —— `--space-1: 4px;`、`--font:14px; --font-sm:13px; --font-xs:12px;`、`html{font-size:var(--font)}`、`body{line-height:1.55}`。政策口径"字号/行高/间距节奏"覆盖的 **49 处硬编码字号、41 处离刻度 gap、14 处离刻度圆角全都不在机器拦截范围内**。
2. 因此本提案把改动分成 **3 个等级**，只有 Tier 1 今天就能做、Tier 2/3 必须等 owner 痛点触发 S6 复议：
   - **Tier 1（零复议）**：钉④ 那 4 条值**一字不改**；字重**显式化**（550/600/650→700、500→400，Windows 渲染结果与现状**完全相同**）；把散落值**映射回已冻结 token**。
   - **Tier 2（需 S6 复议）**：任何**改变渲染结果**的归位（11px→12px、gap 离刻度归位、圆角离刻度归位、表面层分配 A1-②）。理由：钉④ 的立法意图是"字号/行高/间距节奏不许顺手改"，绕过 4 条枚举去改散落值等于绕开立法。
   - **Tier 3（需 S6 复议 + 新增 token）**：扩展刻度（新增 15px 大标题档等）。
3. **推荐组合**：Tier 1 全收 + Tier 2 打包成一个"归一包"**由 owner 痛点勾选一次性触发 S6**（不逐条复议）+ Tier 3 仅在 A2 小样选"档 B"时启用。
4. 与 3 条本地静态钉的一致性自查：**全部通过**（详见 §6），其中"禁 11px/10px"钉是归一包的机器闸，必须**先落钉、再改值**，才能防回潮。

## 6. 与 3 条本地静态钉的一致性自查

3 条钉（`[HANDOFF_TO_CODING]`，落点 `tests/test_gui_js_static.py` 沿用既有钉法）：
① 组件规则内禁止硬编码色值；② `font-size` 禁止 `11px`/`10px`；③ `border-radius` 必须出自 token。

| 钉 | 本提案是否满足 | 证据 / 处置 |
|---|---|---|
| ① 禁硬编码色值 | **通过（有条件）** | 提案**不引入任何新色值**（A1-② 只改 `--bg/--surface/--surface-2` 的**使用位置**，值全部来自 handoff §5）。已知现存违例须随归一包一并消：`style.css:210` `#fff`、`:846` `#fff` → 改 `var(--on-primary)`；`:214/:847` 阴影 → `--shadow-brand/--shadow-primary`。**豁免 1 条**：`style.css:942` select 箭头 data-uri 内描边 `#6B7280` —— `url()` 内无法解析 `var()`，须写入钉的豁免名单（同 impeccable `ignoreRules` 思路） |
| ② 禁 `11px`/`10px` | **通过** | §3.1 全量归位 24 处 → 零残留；钉须**先落、后改值**，才能防回潮 |

**结论：3 条钉与本提案方向一致，无冲突；钉① 需内置 1 条 data-uri 豁免，钉②③ 需在归一包落地后保持零违例。**

## 9. P8 专项说明（impeccable 不装 + 3 钉本地化）

**改判结论：通过。撤回上轮"倾向给 OpenCode 装 hook"的意见。**

对评议员三条新理由的回应：
1. **采纳（决定性）**——本项目规则明定"OpenCode 的自测结果一律视为未验证，完成后由主审验收"。hook 在 OpenCode 编辑 UI 文件时触发的检测结果，**形式上属于"未验证的自测"**，不能作为门；更坏的情形是它被误读成"已经验证过"，污染验收判断。既然无论如何要重跑，hook 的边际价值只剩"提前看到"，不值一份仓库污染。
2. **采纳（决定性）**——3 条 Python 静态钉位于 `tests/test_gui_js_static.py`，天然嵌进验证链"静态检查 → 定向测试 → 全量测试"，**每张卡必跑、失败即停、可先红后绿、可"测试基线只增不减"**。这是 npm hook 结构上拿不到的地位；且 detect 的核心价值（确定性规则、可 CI）被 3 条钉**原地继承**。
3. **采纳（成本判断）**——我上轮 §6 已预判 4 类必然误伤（系统字体栈 / 中性灰 / 嵌套卡 / 30px 控件高 / 侧栏激活条），且归一包期间正是这些项被集中触碰的时段，**噪音峰值与改造期重合**；豁免清单的长期维护落在主模型身上，属持续成本。用一次性 3 条钉替代 59 条规则的长期豁免维护，净收益为正。

**保留意见（不改变结论）**：判"不装 hook"与判"不用 detect"不是一回事。原评估里"重塑开工时手动跑一次 `npx impeccable detect` 做一次性审计"仍有微弱价值（交叉验证我的静态审计），但需**先配 4 条豁免再跑**，且其产出对我已交付的《静态设计审计报告》属**边际增量**。因此降级为**可选**：跑不跑都不影响阶段 0a 完整性；若跑，产出只作咨询、不进验收链。

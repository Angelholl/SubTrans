# 单件卡：C22 听点标注器——长间隙判读辅助（能量提示透传+切片上限放宽+幂等 prepare）

> 决策依据：owner 2026-10-13 试听发现"部分判读区间过长/时间轴长短与内容不符"——根因有三：①manifest 每条携带的粗筛能量提示（message，如"间隙 18046ms 内检测到语音能量约 0.10s"）未透传到标注界面，长间隙里大部分是静音/噪声，owner 无提示白听；②切片时长 cap 20s 会把 >14s 的长间隙尾部截掉（-t min(止-起+6,20)），长间隙尾部根本不在片段里；③±3s 缓冲无说明，相邻已字幕台词混入缓冲易误判。C22 批，依赖卡2/卡3（75cc69f、05692c5）。
> 执行者：OpenCode。只 commit 不 push；卡外问题即停待裁决。

## 根因

三个独立短板叠加造成长间隙判读困难：message 不上屏、切片截断长间隙尾部、缓冲语义无说明。另：当前 --prepare 重跑会整体重写 state.json，owner 已标答案丢失，导致工具升级后无法安全重切。

## 改法（功能规格）

1. **message 透传**：--prepare 读 manifest samples 的 `message` 字段 → `records[].message`（缺省 null）；serve 页 meta 行追加第二行「粗筛提示：<message>」（有则显，esc 转义）。
2. **prepare 幂等（保标注）**：state.json 已存在时，新 records 按 id 合并旧 records 的 `label/sounds/relabel/relabel_sounds`（id 匹配即继承，缺失字段不崩），labeled 计数重算；打印中文摘要含「已保留 N 条既有标注」。clips 重切覆盖（文件名=id 稳定）。
3. **切片上限 20→30s**：`-t min(止-起+6, 30)`（30s≈940KB 16k 单声道 wav，体积可控；30s 以上间隙仍截断但覆盖绝大多数；测试钉 T_D 类长用例同步改）。
4. **播放起点=间隙本体**：render 时若片段时长 >6.5s 且未被起点 clamp（timing 起≥3s），play() 前设 `currentTime=3`（跳过前缓冲）；重听按钮保持从头。JS 侧从 records 数据取不了 clamp 信息——serve 在 state records 里补 `seek_in=3.0|0.0`（prepare 按timing 起<3s 置 0，其余 3.0）。
5. **缓冲说明文案**：作答区提示行前追加一行「片段首尾各约 3 秒为缓冲上下文：只判间隙本体内是否有台词；边缘与既有字幕对齐的台词不算漏听」。

- **实现要点（便于验收比对）**：
  1. message 只透传不加工：`None if msg is None else str(msg)`；空串按「无」处理（JS falsy 不上屏）。
  2. 幂等合并字段集=卡面点名的 `label/sounds/relabel/relabel_sounds` 四字段，仅旧记录**确有该键**才继承（旧态整键缺失→保持新记录默认 null，不崩）；「已保留」计数=四字段任一非 null 的条数；已标注口径=首轮派生已决（yes/no，skip 算待定），与 merge 的 pending 口径同源（`_record_label`）。
  3. `seek_in` 由 prepare 写入 state.json（serve 只透传）：`start < _PAD_BEFORE_S → 0.0`，否则 `3.0`；JS 侧 `seekIn = Number(rec.seek_in || 0)`，故卡面「currentTime=seek_in」静态断言在源码里落为 `currentTime = seekIn`（JS camelCase 局部变量，语义同卡面）。
  4. 切片失败仍整批中止且不写 state.json → 任何失败路径下旧标注零丢失（幂等硬约束的失败侧保证）。

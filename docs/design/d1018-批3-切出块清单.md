## 三、切序与布局口径（为什么不是「依赖序优先」）

D2026-1018-02 已拍板硬原则为「字节守恒＋流序＋函数不跨文件＋品牌＋零构建」，其中**流序**决定：`read_all()` 逐字节等价是唯一总判据，且守恒钉 `787460b7…3533` 在批1-3 恒真。由该约束可得两条切序硬定式：

1. **只能从文件首或文件尾剥离**：中间块切出会使留存文件成为「前段＋后段」的非连续拼接，`read_all()` 立即失配（除非多付一条冻结边界另立残段文件）。
2. **因此切序 = 字节流序**：先按序剥离头部 13 块（#1→#13），再按逆序剥离尾部 3 块（#16→#15→#14…即 #16 先、#15 次、#14 末）。切割序与「依赖序」在本批**等价无风险**——因为每切一块守恒钉不变，全部文件的**加载序＝字节流序**完全保持，运行期符号解析序与拆分前逐字节同构，强于依赖序论证（依赖序只保证「被依赖者先出现」，守恒钉保证「全部字节序不变」）。

**留存终态**：剥离完成后 `app-main.js` = 原 L1936-6293（Refine IIFE，204,060B），即批4 的唯一目标文件；`JS_FILES` 序 = `app.js → app-msg.js → app-modal.js → app-error-handler.js → … → app-main.js → app-init.js → app-encode-dock.js → app-feature-status.js`，`review.js` 恒居末位下位。
